# Data Model: Todo List Application

**Feature**: 001-todo-app
**Phase**: 1 (Design & Contracts)
**Date**: 2026-01-03

## Overview

This document defines the data structures, validation rules, and state transitions for the Todo List application. The model is shared across all three frontend architectures (MVC, MVP, MVVM) and both backend communication modes (REST, Realtime).

---

## 1. Task Entity

### Schema

```typescript
interface Task {
  id: string;              // UUID v4 (e.g., "a3f2c8b1-4d5e-6f7g-8h9i-0j1k2l3m4n5o")
  title: string;           // Task description (1-500 characters, non-empty after trim)
  createdAt: string;       // ISO 8601 timestamp (e.g., "2026-01-03T14:30:00.000Z")
  updatedAt: string;       // ISO 8601 timestamp (updated on edit)
}
```

### Field Specifications

| Field | Type | Required | Constraints | Notes |
|-------|------|----------|-------------|-------|
| `id` | string | Yes | UUID v4 format | Generated by backend on creation |
| `title` | string | Yes | 1-500 chars, non-empty after trim | User-provided text |
| `createdAt` | string | Yes | ISO 8601 datetime | Backend timestamp on creation |
| `updatedAt` | string | Yes | ISO 8601 datetime | Backend timestamp, initially = createdAt |

### Validation Rules

**Title Validation** (enforced by `packages/todo-domain/src/taskRules.ts`):

```typescript
function validateTitle(title: string): { valid: boolean; error?: string } {
  const trimmed = title.trim();

  if (trimmed.length === 0) {
    return { valid: false, error: "Title cannot be empty" };
  }

  if (trimmed.length > 500) {
    return { valid: false, error: "Title cannot exceed 500 characters" };
  }

  return { valid: true };
}
```

**Enforcement Points**:
- **Frontend**: Immediate validation on input (prevents submit/save if invalid)
- **Backend**: Re-validates on POST/PUT (prevents malicious requests)

## 2. TaskList Collection

### Structure

```typescript
interface TaskList {
  tasks: Task[];           // Array of tasks, ordered newest first
}
```

### Ordering Rules

- **Sort Key**: `createdAt` timestamp (descending)
- **Order**: Newest tasks first (reverse chronological)
- **Implementation**: Backend returns sorted array; frontend displays as-received
- **New Task Insertion**: Prepend to array (index 0)

**Example**:
```typescript
const taskList = {
  tasks: [
    { id: "uuid3", title: "Task C", createdAt: "2026-01-03T15:00:00Z", ... },  // newest
    { id: "uuid2", title: "Task B", createdAt: "2026-01-03T14:30:00Z", ... },
    { id: "uuid1", title: "Task A", createdAt: "2026-01-03T14:00:00Z", ... }   // oldest
  ]
};
```

## 3. State Transitions

### Task Lifecycle

```
┌─────────────────────────────────────────────────────────────┐
│                       Task Lifecycle                         │
└─────────────────────────────────────────────────────────────┘

  [User creates task]
         │
         ▼
  ┌──────────────┐
  │   CREATED    │ ← Initial state (id + createdAt + updatedAt generated)
  └──────────────┘
         │
         ├──────────────────────────────────────────────┐
         │                                               │
         ▼                                               ▼
  ┌──────────────┐                               ┌──────────────┐
  │   UPDATED    │ ← title modified               │   DELETED    │ ← Removed from store
  └──────────────┘   (updatedAt timestamp)       └──────────────┘
         │                                               │
         │                                               ▼
         └───────────────────────┐                  [Permanent]
                                 │
                                 ▼
                          ┌──────────────┐
                          │   UPDATED    │ (can edit multiple times)
                          └──────────────┘
```

### State Details

**CREATED**:
- **Trigger**: User submits TaskForm with valid title
- **Action**: Backend generates UUID, timestamps (createdAt = updatedAt)
- **Result**: Task appears in list at position 0 (top)

**UPDATED**:
- **Trigger**: User saves inline edit with modified title
- **Action**: Backend updates title, sets updatedAt to current timestamp
- **Result**: Task remains in same position (createdAt unchanged)
- **Note**: Can transition to UPDATED multiple times

**DELETED**:
- **Trigger**: User clicks delete button (no confirmation)
- **Action**: Backend removes from storage
- **Result**: Task disappears from list
- **Note**: Terminal state (no recovery)

### No State Tracking

The application does **not** track intermediate states like:
- "Pending save" (optimistic updates not implemented for clarity)
- "Syncing" (sync happens immediately or on next poll)
- "Conflicted" (last-write-wins, no conflict resolution)

This simplicity aligns with Principle VII (Simplicity and Focus).

## 4. Persistence Strategy

### Backend Storage

**Primary Store**: In-memory `Map<string, Task>`

```typescript
class TaskRepository {
  private tasks = new Map<string, Task>();

  getAll(): Task[] {
    return Array.from(this.tasks.values())
      .sort((a, b) => new Date(b.createdAt).getTime() - new Date(a.createdAt).getTime());
  }

  create(task: Task): void {
    this.tasks.set(task.id, task);
  }

  update(id: string, updates: Partial<Task>): Task | null {
    const existing = this.tasks.get(id);
    if (!existing) return null;

    const updated = { ...existing, ...updates, updatedAt: new Date().toISOString() };
    this.tasks.set(id, updated);
    return updated;
  }

  delete(id: string): boolean {
    return this.tasks.delete(id);
  }
}
```

**Optional File Persistence** (for demo durability):
- File: `apps/backend/data/tasks.json`
- Write: On every mutation (create/update/delete)
- Read: On server startup
- Format: JSON array of Task objects

**Rationale**: In-memory is sufficient for demo (Assumption 5), but file persistence prevents data loss during development restarts.

### Frontend Cache

**No Client-Side Persistence**:
- Tasks loaded from backend on app mount
- State held in memory only (TaskStore instance)
- Page reload = fresh fetch from backend

**Rationale**: Simplifies state synchronization and avoids stale cache issues in demo.

## 5. Concurrent Editing Behavior

### Strategy: Last-Write-Wins

**Scenario**: Two users edit the same task simultaneously

1. User A edits "Buy groceries" → "Buy organic groceries" (saves at T1)
2. User B edits "Buy groceries" → "Buy local groceries" (saves at T2)
3. Result: Final title is "Buy local groceries" (T2 overwrites T1)

**Justification**: Assumption 6 states "Last-write-wins conflict resolution is acceptable for the academic demonstration."

**Implementation**:
- No version tracking (no `version` field)
- No optimistic locking
- Backend blindly overwrites on PUT /tasks/:id
- Realtime mode broadcasts latest state to all clients

### Edge Case Handling

**Deleted Task Edit Attempt**:
- User A deletes task at T1
- User B tries to edit same task at T2
- Backend returns 404 Not Found
- Frontend shows error message: "Task no longer exists"

**Rapid Edits**:
- Multiple quick edits from same user
- Each triggers separate PUT request
- Last request wins (previous in-flight requests may arrive out-of-order)
- Acceptable per demo scope

## 7. ID Generation

### Strategy: UUID v4

**Implementation**:
```typescript
import { v4 as uuidv4 } from 'uuid';

function generateTaskId(): string {
  return uuidv4();  // e.g., "a3f2c8b1-4d5e-6f7g-8h9i-0j1k2l3m4n5o"
}
```

**Location**: Backend only (apps/backend/src/domain/taskService.ts)

**Rationale**:
- Collision-free (astronomically low probability)
- No coordination required across instances
- Standard library support

**Alternatives Considered**:
- Auto-increment integers: Rejected (requires centralized counter, complicates distributed scenarios)
- Timestamp-based: Rejected (not unique if multiple tasks created in same millisecond)

## 8. Timestamp Format

### Standard: ISO 8601

**Format**: `YYYY-MM-DDTHH:mm:ss.sssZ`

**Example**: `2026-01-03T14:30:45.123Z`

**Generation**:
```typescript
function now(): string {
  return new Date().toISOString();
}
```

**Parsing**:
```typescript
function parseTimestamp(iso: string): Date {
  return new Date(iso);
}
```

**Rationale**:
- Unambiguous (always UTC)
- JSON-serializable (string)
- Sortable lexicographically
- Standard JavaScript support

## Summary

| Aspect | Specification |
|--------|---------------|
| **Entity** | Task (id, title, createdAt, updatedAt) |
| **Ordering** | Reverse chronological (newest first) |
| **Validation** | Non-empty title, 1-500 chars |
| **Persistence** | In-memory Map + optional JSON file |
| **Concurrency** | Last-write-wins |
| **ID Generation** | UUID v4 (backend) |
| **Timestamps** | ISO 8601 (UTC) |
| **States** | CREATED → UPDATED* → DELETED |
| **Empty State** | Display message when tasks.length === 0 |

This data model ensures consistency across all frontend architectures and backend modes while maintaining simplicity per Principle VII.
